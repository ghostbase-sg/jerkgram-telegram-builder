## Lifecycle hooks and weak registry

`submodules/TelegramCore/Sources/Account/Account.swift`: public `id: AccountRecordId` and `basePath: String` (1385–1386), initializer receives the id (1484). Use `Account.id` internally to route teardown notifications; export only random scope id, never AccountRecordId. Account owns its recorder and bridge; Network holds weak epoch-bound context. Register only confirmed bot, non-supplementary normal Account scopes. A supplementary Account created by cleanup must not register a new diagnostic scope or launch history. Normal users have no entry.

Minimal explicit lifecycle registry may be a small process-wide TelegramCore helper keyed by AccountRecordId, with **weak** scope values and generation token. This is a narrowly owned teardown index, not a global network hook. Cap it (e.g. 32 live slots), purge dead entries during insert/lookups; do not evict an active cancellation target silently. If full, fail closed for new experimental bridge start and mark bounded coverage loss; ordinary user behavior unchanged. Registry lookup copies a weak target/generation under its short lock, releases lock, then calls scope freeze-and-cancel. No callbacks, filesystem work, Postbox transactions, or arbitrary dispatch under registry lock. Compare generation on removal so old deinit cannot unregister a replacement. Prefer app-instance ownership/injection if actual AccountManager lifetime permits it without broad refactor; a static registry must distinguish manager namespaces if multiple manager roots can share ids. Exact full-tree AccountRecordId uniqueness across manager roots is not established here, so do not assume it.

Scope freeze-and-cancel first invalidates bridge generation and copies bounded redacted in-memory lifecycle snapshot, detaches Network registration, and enqueues snapshot to the independent sink. It then cancels bridge-owned work on its proper manager queue; cancellation must not touch modern outbound disposables or block logout. An already executing Postbox transaction may complete; invalidation prevents subsequent page/import scheduling. A sink queue receives copied values only, with no Account retention. Frozen snapshot handoff is best effort and asynchronous, not guaranteed durable before cleanup/crash. Ensure lifecycle reserved queue slots survive ordinary saturation.

## Availability after bot logout

An action gated only on the currently open bot Account vanishes when that account is removed. To support required post-logout export, show the BOTBRIDGE1 diagnostic action in experimental Settings Data and Backup whenever the global sink has retained sessions, even from another active user account. This creates no user recorder entry and exports only the explicitly labeled retained BOTBRIDGE1 sessions. Avoid filtering by current account alone. For zero accounts, this Settings screen is inaccessible: the minimal integration cannot guarantee an in-app export action on the login screen. Documents/Jerkgram/BotBridge1 may be an alternative only if actual app Files sharing configuration exposes it; that capability has not been established. If no-account in-app export is required, a separate login-screen/settings entry is an explicit additional UI task. Do not promise it from the existing screen.
