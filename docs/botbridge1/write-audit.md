## Auth/account lifecycle

`Account/Account.swift` creates modern pending send/edit owners with the same `network`, `postbox`, and `stateManager` (1607–1614). `network.loggedOut` (1617) ordinarily sets `_loggedOut` and drops calls (1635). **Staged BOTSHADOW1 currently returns early while `GhostBaseBotHistoryGate` is active**, suppressing the logout callback. This is existing experimental behavior, not neutral diagnostics; BOTBRIDGE1 should restore normal lifecycle handling within its scoped branch. Do not infer that the historical request caused logout from this comment or gate.

`network.didReceiveSoftAuthResetError` (1639) is a separate observation; it does not itself remove the account. `Network/Network.swift`: `loggedOut`, `permanentKeyUnknown`, `didReceiveSoftAuthResetError` properties 983–988; context logout callback 1069; `mainSessionAuthorizationRequired` 1283; soft-reset forwarding 530. These events may arrive on other queues and may precede per-RPC error delivery. `permanentKeyUnknown` carries an auth key id: do not log its argument or network/context description.

`Account/AccountManager.swift`: `logoutFromAccount` (369) writes loggedOut attribute; `managedCleanupAccounts` (395) observes records and cleans account directories; `cleanupAccount` (484) may call `auth.logOut` (508) and handle future auth token (516). Log event types and local diagnostic account id only, never this token. Record logout requested, remotely already logged out, record marked, cleanup started/completed, and removal separately. Callback is not identical to removal.

Existing `ghostBaseBotSafeRecord` in Account.swift (1345) writes UserDefaults twice on caller queue, includes raw peer id, and has a global last-event key that multiple accounts overwrite. It is insufficient as the new correlation logger. Do not call it at every send progress tick or repurpose it as the new hot-path sink.

## Bounded diagnostic design (proposal, not implementation)

Place shared internal recorder declarations in an existing TelegramCore source owner (e.g. Account.swift) to avoid a new Bazel source target. Give each Account lifetime a random opaque diagnostic id and session epoch; do not derive it from token, auth key, peer id, username, or message content. Network may hold a weak/callback reference to that account-local recorder. Destroy registrations on Account teardown/removal; use generations so queued results from an old login cannot attach to a new Account.

Use one queue-confined ring per account: e.g. 256 events, 64 active logical operations, 8 frozen auth snapshots, with a documented TTL (e.g. 30 minutes for correlation). Fields: opaque account/session id, monotonic sequence, wall timestamp and monotonic delta, logical operation id, attempt number, finite action flags (text/reply/media/post/reaction/edit/delete/other), finite phase (intent/queued/upload/request/ack/result/applied/failure/cancel/timeout), finite error class and numeric code. Classify before storing; never retain API requests/responses, text, captions, media paths, peer/message ids, raw error descriptions, credentials, or context `description`.

Use an in-memory mapping from modern local message/operation key to opaque operation id solely to join enqueue to actual worker RPC; never export key. Reply/media/post are independent flags because a reply may carry media and a channel post may be text. Capture classification at intent or worker transaction, not from serialized RPC payload logging. Give batched/album operations parent/child identifiers. On retries preserve logical id, increment attempt; instrument actual subscription per attempt so cold Signal construction is not mistaken for dispatch. Do not change operators, network dependency tags, flood waits, retries, update application, or disposal semantics. Observe errors before existing mapError/catch; preserve the original error untouched. `next` acknowledgement is not success; success means RPC response, with separate local apply marker.

On auth event atomically snapshot most recent **dispatched**, most recent completed, and all currently in-flight operations with ages and result classes. Include `none`, `expired`, or `history_lost` explicitly. Store intent separately: a queued operation may never reach the network. Callback order is a partial order across queues; timestamps/sequence show observation ordering, not server causation. Freeze before logout cleanup clears mappings. Do not suppress, postpone, or retry auth failures for logging.

Bound both recorder and its asynchronous delivery backlog; a serial DispatchQueue alone is unbounded. Drop/coalesce diagnostics when full, increment loss counter, reserve lifecycle snapshot slots, and include evicted-event/operation counts. Retire mapping on result/cancel/timeout; cap TTL and record evicted-active as unknown. App kill, restart, disabled logger, ring overflow, and queue drops must be visible as coverage gaps. Retain an explicitly bounded redacted final auth snapshot asynchronously in app-level diagnostic storage before account-directory cleanup where practical; it cannot guarantee crash durability. No synchronous file I/O/UserDefaults writes in enqueue, RPC, network, UI, or update callbacks. Batch asynchronous writes, rotate bounded files, allow export; no upload/progress/per-frame events. Cleanup must release disposables and maps without disposing real outbound work.

## Minimal passive Network alternative

Preferred first diagnostic increment if preserving modern worker files byte-for-byte is the priority: instrument the two existing source-native functions in `Network/Network.swift`, `requestWithAdditionalInfo<T>` (1374) and `request<T>` (1420), plus existing Account lifecycle callbacks. Both accept `(FunctionDescription, Buffer, DeserializeFunctionResponse<T>)`, dependency `tag`, flood-wait policy options; both return cold Signals whose subscription constructs a `NetworkEngineRequest` and invokes `requestService.add(request)`. This is a real request submission boundary, although the transport may still queue it; label it `submitted`, not `server_received` or wire-dispatched. Observe before delivering to subscribers. Preserve all data, metadata, parse, options, dependency, callbacks and error policy behavior.

The first function supplies `acknowledged` and `completed` closures; the second deliberately supplies `acknowledged: nil`. Preserve that choice: report ack only where already available, rather than changing transport callbacks to increase coverage. Ignore `progress`. In both completed closures distinguish success with valid `T` from local `TL_VERIFICATION_ERROR` and transport `.failure(failure).error`; the parse failure must not be called successful merely because transport completion was success. Record finite error classification before passing original MTRpcError unchanged. A disposable wrapper can mark `disposed_before_terminal`, while disposing the original exactly once and immediately; synchronize terminal state because completion/disposal can race. Signal machinery routinely disposes after completion, which must not create a false cancelled event. Disposal only proves subscriber cancellation, not that the server did not execute a mutation.

Each subscription allocates an independent opaque request id inside its Signal closure, not when the Signal is constructed. Retries that resubscribe therefore receive separate request ids. This is exact request/result/auth-event correlation without logical-message joining. Transport-internal retries may remain inside one subscription; optionally wrap the existing `shouldContinueAfterError` closure per request, observe bounded finite retry metadata, then return the original policy result unchanged. Do not alter the global policy function or add global hooks. Confirm actual `NetworkEngineErrorContext` definition before implementation: staged policy establishes only `floodWaitSeconds`, `floodWaitErrorText`, `internalServerErrorCount`; it does not prove raw MTRpcError is exposed there. Never log floodWaitErrorText. Rate-limit retry events and keep a count. This hook alone cannot prove number of wire attempts or all intermediate auth errors.

### Safe FunctionDescription interface

Official pinned `submodules/TelegramApi/Sources/DeserializeFunctionResponse.swift` defines `public final class FunctionDescription` with `public let name: String`, and `public var parameters: [(String, ConstructorParameterDescription)]`. `ConstructorParameterDescription.value` is `Optional<Any>`. Parameters are produced lazily under NSLock and cached. Official `TelegramApi/Sources/TLObjectSupport.swift` `tlFunctionParts` builds name from the schema constructor and lazyParameters via `tlDescriptionFields(call).1`. Accessing parameters materializes all request fields including message/quote text and nested peer/reply objects. Therefore **read only `.name`**, map an exact allowlist to finite labels, and never call description/string interpolation, `.parameters`, serialization, reflection, or buffer parsing for diagnostics. Existing `WrappedFunctionDescription.name` in Network.swift 37 confirms direct name availability; its `.description` calls apiFunctionDescription and is inappropriate here. Validate actual schema names against this pinned API in a fixture before hardcoding the whitelist.

Method names classify sendMessage, sendMedia/sendMultiMedia, sendReaction/sendPaidReaction, editMessage, deleteMessages and channels delete variants, forwards/inline-result and optionally explicit account/group mutation methods. Keep a checked finite registry; an unlisted mutation is a coverage gap. This covers the listed normal modern message workers and standalone workers because their real terminal RPCs call these Network functions. It is not a universal hook: `MultiplexedRequestManager.swift` has its own request path; `Network/Download.swift` has separate request builders, and uploads may bypass these two functions. Those must be excluded explicitly from claims (media terminal send result is covered; upload failure may have no terminal send RPC). Likewise server update application is not covered by Network result alone.

### Reply/post classification and joining limits

Name-only diagnostics can identify sendMessage versus sendMedia but cannot tell whether a request is a reply, channel post, scheduled send or user chat. InputPeer/InputReplyTo values exist inside lazy request parameters, not in the Network function's typed arguments. Even inspecting `inputPeerChannel` would not distinguish broadcast channel from megagroup; replyToMessage also carries topic/monoforum routing that must not automatically count as an explicit user reply. Official PendingMessageManager uses `Api.InputReplyTo?` around 1834/1910/2015/2040 and constructs `.inputReplyToMessage(.init(...))`, including zero-id monoforum routing around 2096–2111. Reading the actual user intent and resolved peer kind in the worker transaction is more reliable.

Minimal `EnqueueMessage.message` intent hook may emit independent flags `text`, `reply` from explicit reply subject, `media`, `post` from modern resolved broadcast peer, and its own opaque intent id; no content or local ids exported. These intent events are useful but **cannot be honestly joined to Network request results** from timing or category alone. The Network interface carries no local message id or enqueue correlation id. `NetworkRequestDependencyTag` controls ordering and is not a diagnostic context; do not replace/extend its semantics, assume dynamic casts, or infer mappings from request buffers. An enqueue-only dictionary keyed by local ids does not solve the missing key at Network. Forward/media albums, retries, scheduled sends, standalone paths and concurrent sends make nearest-intent matching ambiguous.

Consequently choose explicitly: (A) preserve all worker hashes and provide exact request-method outcome plus separate unjoined intent stream, with reply/post RPC classification `unknown`; or (B) propagate an explicit opaque diagnostic context at modern worker call sites to Network, adding a defaulted internal parameter without changing RPC algorithms, and obtain exact logical action/result joining. Option B still needs the worker owners audited above (including standalone, group, edit/delete/reaction if logical ids are desired). An alternative narrow worker-side classification callback alongside the real request can join the opaque request id only through an explicit API contract; do not use thread-local state across asynchronous Signals. Do not present option A as satisfying exact reply/post outcome evidence by itself.

### Ownership and tests for the minimal option

Account owns the bounded recorder and installs a weak account-local context on its existing Network only after confirming bot identity. Registration must be thread-safe, epoch-bound and disposable; no global network registry or swizzling. Resolve the weak context at actual subscription, capture only its opaque generation and finite method class, and ignore callbacks if that Account generation expired. Avoid retaining Account via returned Signals. Preserve normal accounts' fast path and all existing network stack behavior. Snapshot most recent submitted/result and in-flight request ids on logout/soft reset/removal; use `unknown cause` language. Capture the snapshot before unregistering, then clear mappings and weak registration on teardown. Queue/storage bounds and loss visibility from the primary proposal still apply.

Test actual cold Signal reuse/resubscription, ack-before-result, completion then disposal, cancellation race, TL verification failure, retry-policy return equivalence, bot registration lifetime, late callbacks after relogin, two Networks/accounts interleaved, and forbidden sentinel privacy. Assert unregistered calls preserve `requestService.add` / returned-disposable behavior and do not instantiate diagnostic state. Source hash comparison can demonstrate PendingMessageManager/EnqueueMessage/RequestEditMessage/MessageReactions/delete workers remain unchanged under option A; test fixtures must state that reply/post intents remain unjoined and upload failures are out of scope. Full compile and runtime validation remain mandatory.
