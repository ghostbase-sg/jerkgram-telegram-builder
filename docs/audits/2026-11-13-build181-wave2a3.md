## Proven redundant work (one fix)

Owner: `submodules/JerkgramCore/Sources/JerkgramStore.swift`, `JerkgramJSONLEventStore.filteredRecords`.

Call path: visible chat visit -> `JerkgramCaptureRecorder.requestChangesSinceLastOpening` -> existing serial utility queue -> `store.readyIndexRecords(afterSequence:previous)` -> shared index lock -> filteredRecords. `indexRecords` uses the same helper. Each opening previously scans the entire cached chat bucket, filters and sorts its output while the global store lock is held. For a large archived chat and recent watermark it repeats work over mostly unchanged records.

Invariant already established by all actual cache owners: `groupedRecordsByChat` sorts each bucket by sequence/eventId on index build/reload; append sorts each addition and either appends after the last record or `mergeAscending`s overlapping/out-of-order additions. `recordsByChat` is private, account-scoped and never supplied by UI callers.

Fix: two binary upper bounds over sequence, then copy the selected contiguous slice. Equal-sequence eventId order remains the existing order. No sequence+1 arithmetic, so Int64 extrema remain safe. Empty/reversed ranges return empty. Existing index file-size validation and invalidation remain. No new cache, timer, observer or worker.

Expected algorithmic cost: `O(chat records + result sorting)` -> `O(log chat records + returned records)`. Native actual-fragment matrix measures record-property accesses for 50,000 records and 18 returned records; numbers are pending execution on macOS, not reported as observed yet. This is not an FPS/thermal claim.
