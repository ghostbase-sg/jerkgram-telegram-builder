# Stable182 bot chat history and native sending

Baseline GREEN181 `3b5d0b51e9289c14f595e097619b04ade70444d6`, Telegram13.2 `24638bc69bd083981b178dd1e7f921eebbf7fc46`. Device evidence: dialog history now present, individual messages/composer unusable. No real-account tests.

## Root causes and changes

1. **P1 visible history:** imported `.Random` historical messages coexist with durable holes. Native `HistoryViewState` clips/waits around those holes; bot hole fetching deliberately cannot fill them. Merely setting `trackHoles=false` affects scheduling, not clipping/loading. `Postbox/MessageHistoryView.swift` adds explicit default-OFF `locallyAvailableOnly`, constructing loaded view state with empty **in-memory** holes; resets and transaction hole operations honor it. Persistent holes, message identities, read states and normal account behavior are unchanged. Existing native loaded-state pagination/order sampler stays intact.
2. **P1 scope and initial load:** `TelegramCore/State/AccountViewTracker.swift` selects this mode only after transaction checks the current account's self TelegramUser.botInfo. The three ordinary history entry points use it; native user accounts keep original signals. `TelegramUI/ChatHistoryViewForLocation.swift` stops waiting for optional BusinessIntro hydration for genuine bot accounts. Native supported-account intro behavior unchanged.
3. **P1 sending:** native PendingMessageManager destination `apiInputPeer` returns nil when a referenced user has no hash, or uses a generic/min hash as full. Telegram explicitly requires bots to use zero when only a min/no hash exists ([peer contract](https://core.telegram.org/api/peers#access-hash)). New transaction-scoped `botBridgeInputPeerForSending` verifies actual self botInfo, preserves personal hashes, uses zero only for bot user/channel/community destinations. Both modern individual/group send boundaries and forward source conversion use it. Native sendMessage/sendMedia/sendMultiMedia request construction, authorization, flood handling and live update paths unchanged. No Bot API substitute or global bot spoof.
4. Replay can fill only a missing personal hash of an already present referenced user. `botBridgeMergeHistoricalPeer` + `TelegramUser.withUpdatedAccessHash` preserve every current metadata field; no old flags/permissions/name replaces current state. Message IDs must be positive cloud IDs. Existing message identity/content remain. No metadata-only history replay/migration: accepted history policy/progress codec unchanged.

New pinned native inputs absent from the selected local projection: MessageHistoryView.swift and ChatHistoryViewForLocation.swift. Original blobs, plus native sampler/API conversion, are retained under `tests/fixtures/stable182/bot-native`; Git blob hashes are asserted. They are ordinary existing upstream files in genuine CI checkout, not invented source files.

## Verification and limits

Focused tests: seven local source/assembly/provenance checks PASS; two native tests pending macOS (actual importer/view/peer functions and genuine Postbox codec at -Onone/-O). Public Postbox wrapper forwarding and argument order reviewed explicitly, not just internal implementation. Frozen EnqueueMessage/StoreMessage/Authorization/CanSendMessagesToPeer and history policy hashes retained in fixture. One combined successor gate refuses native skips in CI.

No device success claim. View exposes **locally available** messages and cannot promise Telegram returned all past messages. Existing bounded Build181 history/live mechanism remains. Device must check opening old bot chat, older pages, text/photo send, replies/new incoming updates and ordinary account chat behavior. Existing data must not be cleared or account relogged merely to test this repair.
