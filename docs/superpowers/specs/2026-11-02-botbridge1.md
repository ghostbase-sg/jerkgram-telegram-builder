Продолжаем разработку Jerkgram. Нужно сделать экспериментальную гибридную ветку **BOTBRIDGE1**.

## Цель

Получить bot-account, который одновременно:

1. умеет получать/восстанавливать **старую историю сообщений** доказанно рабочим механизмом GhostBase Build 82 / v1.0ZC;
2. использует **современную архитектуру последнего рабочего Jerkgram** для всех исходящих действий:
   - отправка сообщений;
   - ответы;
   - реакции;
   - отправка медиа;
   - редактирование;
   - удаление;
   - постинг и остальные поддерживаемые действия;
3. сохраняет современную стабильность bot-account и не возвращает старую архитектуру Build82 целиком.

Это НЕ перенос современного Jerkgram назад на Telegram 12.9.2.

**База должна быть современной. Build82 нужен только как источник legacy history/read-механизма.**

# Современная база

Использовать **последний доказанно рабочий source-based Jerkgram на Telegram iOS 13.1.1 / Build175 либо более новый текущий эквивалент этой линии, если Build175 уже был продолжен без изменения bot-account архитектуры**.

Сначала определить точный commit последней GREEN сборки современной линии и зафиксировать его в checkpoint.

Не использовать старый Telegram 12.9.2 как основу BOTBRIDGE1.

Не использовать binary patching.

# Главный архитектурный принцип

Разделяем:

### READ / HISTORY

Legacy Build82/v1.0ZC mechanism.

Только то, что требуется для:

- bot-account historical bootstrap;
- получения старого backlog;
- необходимой работы `getDifference`/state bootstrap;
- импорта старых сообщений;
- восстановления соответствующих peers/chats;
- сохранения полученной истории локально.

### WRITE / INTERACTIONS

ТОЛЬКО современный Jerkgram.

Все действия, изменяющие состояние на сервере, должны идти через текущий Telegram 13.1.1/Jerkgram stack:

- send message;
- reply;
- reactions;
- media;
- edit;
- delete;
- channel/group actions;
- и любые другие outbound RPC/actions.

**Legacy Build82 layer не должен становиться владельцем современных outbound operations.**

---

# Очень важно: НЕ создавать две независимые Telegram state machines

Не должно быть:

- двух Account;
- двух Network;
- двух Postbox;
- двух параллельных владельцев `pts/qts/date/seq`;
- двух независимых update loops.

Должны оставаться:

- ONE Account;
- ONE Network;
- ONE Postbox;
- ONE современный AccountStateManager после завершения bootstrap.

Build82 history logic должен быть ограниченным legacy bridge/importer, а не вторым постоянно работающим Telegram-клиентом внутри Jerkgram.

---

# Предпочтительная архитектура

Условно:

```text
                    BOT ACCOUNT
                        |
              +---------+---------+
              |                   |
       LEGACY HISTORY          MODERN RUNTIME
          BRIDGE               JERKGRAM 13.1.1
              |                   |
       old backlog                live updates
       old history                messages
       bootstrap                  replies
       getDifference              reactions
              |                   media
              |                   edits
              |                   posts
              |                   etc.
              +---------+---------+
                        |
                 MODERN POSTBOX
                        |
             MODERN AccountStateManager
```

Legacy bridge должен использоваться для получения исторических данных, после чего сообщения должны попадать в современное локальное хранилище.

После bootstrap владельцем текущего Telegram state снова является современная архитектура.

# Что уже есть в современной линии

В Build175 уже есть bot live persistence/replay.

Из существующих тестов следует, что современная линия рассматривает live bot replay отдельно от unavailable server history.

Есть `jerkgramIncludeBotMessagePeers(...)`, который работает после добавления сообщений в Postbox и локально включает bot chats, не двигая существующий archive/pinning/history cutoff.

Нужно максимально использовать эту современную инфраструктуру.

То есть предпочтительно:

**Build82 получает legacy messages → преобразование в современный StoreMessage/update representation → современный Postbox/replay/inclusion.**

Не тащить весь старый Postbox/state-management слой, если этого можно избежать.

Логировать:

- начало legacy bootstrap;
- исходный current state;

- количество `getDifference` iterations;
- количество импортированных messages/chats;
- завершение legacy bootstrap;
- переход обратно на current state;
- каждую категорию outbound operation:
  - text
  - reply
  - reaction
  - media
  - edit
  - delete
  - post
- server errors;
- auth/session errors;
- logout;
- soft reset;
- account removal;

- bot token;

- message text;
- приватное содержимое сообщений;

и

- что изменилось;
- почему;
- какое поведение Build82 сохраняется;
- какое невозможно сохранить буквально.
